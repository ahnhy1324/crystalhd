# BCM70015 hardware validation

Current evidence through September 27 is summarized first; the dated sections
retain reproduction recipes, hashes, superseded failures and their fixes.
This is bounded BCM70015 validation, not closure of the complete
[hardware matrix (#8)](https://github.com/ahnhy1324/crystalhd/issues/8).

| Current bounded result | Evidence / limit |
| --- | --- |
| Local H.264 playback | GStreamer 360p/720p pause, seek and rate controls pass; 720p H.264 + AAC runs for 30 minutes with 54000/54000 pictures and EOS. Clocked sinks, not visible/audible proof. |
| Full HD throughput | Opt-in L0s workaround: 900/900 VA-API pictures at 41.20 fps and a 120-second 1080p30 clocked A/V pass. Default link remains below 30 fps. Not Full HD 2x or physical display validation. |
| VA-API correctness | Tested H.264 profiles, complete tails, seeks, retained pictures, one resolution-change sequence and real DMA-BUF image/export reads pass. Backend remains H.264-only. |
| Other codecs | Limited MPEG-2 progressive/interlaced and VC-1/WMV3 fixtures pass. HD WMV3 is 1440 pixels wide, not 1920. |
| Browsers and VLC | Local Chrome software tests pass; live YouTube controls/A/V and Chromium hardware remain unresolved. Stock PowerVLC still misses four tail pictures and fails half-speed transition checks; stock VLC/EGL presentation is unvalidated. |

## Reference system

- PCI: Broadcom BCM70015, `14e4:1615`, on an Intel ICH8 root port.
- Kernel: Ubuntu `6.17.0-41-generic`, x86-64 with i386 userspace support.
- Firmware: `/lib/firmware/bcm70015fw.bin`, identical to the repository copy;
  SHA-256 `8bf3a68f5c64686358a52274e40911a88c7f8c67ecbf6cf1557a49b4d7bc67c9`.
- Library API reports driver `3.10.0`, DIL `3.22.0`. These version numbers do
  not distinguish source revisions; local library/frontend paths were forced.
- Initial/reference module: `8A4E42764F14473E9562951`; an earlier repeated
  matrix also passed on `719593602CEFFABAD916D4F`. The former additionally
  serializes firmware pause/resume callbacks. Unless stated otherwise,
  later userspace tests retained this module and firmware.
- Opt-in L0s candidate: `11356398D0730685483E554`, tested temporarily and then
  replaced by the reference module. On this BIOS-owned link its raw fallback
  restores saved L0s bits on unload; PCI-core-owned policy is deliberately
  sticky and was not exercised on this host. No permanent install is implied.
- Full logs and generated samples are retained in a private local validation
  directory, outside this repository; they are not portable test prerequisites.

Conventions throughout: pin totals are global supporting evidence, not
per-device leak instrumentation; clean playback log windows exclude expected
malformed-ioctl failures. The initial final window began
`10:47:26.825271 +09:00`; microsecond boundaries avoid same-second contamination.
Ordinary playback/forced process cleanup produced no new oops, BUG or hung-task
report. Stop-failure injection, concurrent suspend and physical removal are not
implied. The decode-order experiment settled pins at `3232593 / 3232593`.

pointer. Reload tests successful reprobe, not allocation/PCI-enable injection.

the library's warning-enabled checks; this initial round did not enable them globally.

10-second error bound made FFmpeg fail honestly. Requesting decode order at
startup and via `SET_DISPLAY_ORDER` was ineffective (`GET_DISPLAY_ORDER`
still reported display order), so those commands were removed. Ordinary EOS
without restoring references is invalid for later non-IDR input; the following
batch/replay fix preserves the actual IDR prefix instead.

## Reproduction

compare `/sys/module/crystalhd/srcversion` with `modinfo -F srcversion
driver/linux/crystalhd.ko`. No preexisting player may use the card during the
probes. The following commands use the in-tree library/frontend:

```sh
sh tests/ioctl-smoke.sh
```

## Follow-up: VA-API drain and seek

The fix puts the access-unit delimiter at the start of its timestamped packet.
After 100 ms sync grace, real EOS seals a finite batch; new input waits for
all timestamps and the hardware EOS marker. Full device reopen replays the
retained actual-IDR prefix without overwriting completed private pictures.
Unknown/zero timestamps and exhausted cache/replay limits fail honestly.

All three FFmpeg CLI runs produced exactly 62208000 bytes
(`640 × 360 × 1.5 × 180`) with no duplicate/drop counts. No replay reopen was
needed in these concurrent-input runs. Reported FFmpeg processing speeds were
2.94×, 2.90×, and 2.74× respectively; these are file-decode measurements, not
browser/display performance or guarantees for other clients.

### FHD bottleneck follow-up (2026-09-27)

Historical pre-L0s baseline, using the same 900-picture fixture (SHA-256
`fe186d05ceb384d38f6b674c98da84bd3285e00aee00651c001ea1d62b176d59`)
with unchanged firmware and module `8A4E42764F14473E9562951`:
baseline `7373059` produced 900/900 at 27.30 fps;
fused SSE2 YUY2-to-NV12 conversion produced 900/900 at 27.29 fps. Neither
run dropped or duplicated frames. User CPU time fell from 17.41 to 15.94 s
(system time 2.94 to 3.06 s), but wall time stayed 33.58 s. This is a CPU
cost reduction, not a real-time or display-playback fix.

Scalar rounding/odd edges remain exact across 316 original + 1,170 boundary/
alignment cases; SSE2/scalar sanitizer suites pass. Fresh 180-picture outputs
are identical, each 559,872,000 NV12 bytes, SHA-256
`3297f0792877072ea4f4cddf3ec4149ae52b1e42516465218a0b7d52156488f4`.
This is current-baseline equivalence, not a new independent software comparison.

Direct-library no-copy decoding also returns all 900 pictures, genuine
firmware EOS and clean teardown in 33.05 s, using only 6% CPU. Kernel probes
pair all 902 RX submissions/completions (including control outputs): average
submission-to-completion 34.703 ms, with 14–15 free capture buffers at posting.
Picture-ready notification to posting is 8–32 microseconds. The long interval
includes firmware and device transfer; it does not prove PCIe saturation.

Discarded RX scatterlist experiment: average 608 rather than per-page entries,
27.20 fps, 34.802 ms submission-to-completion; original module restored, no
install/PCIe change. Startup DMA debug `0x10` has single-read/write-queue bits
clear, but does not measure runtime occupancy.

TX-only status-bit forwarding avoids unwanted RX metadata peeks without
changing legacy VC-1 FIFO selection: 10/104 checks fail before, all pass after
on native/i386 and sanitizers. Full checks pass. Restored-reference-module
900/900 retest: 27.28 fps, 33.59 s, user/system 15.99/3.02 s; no drops,
duplicates, kernel errors or references; pins `115309611 / 115309611`.
The L0s follow-up below supersedes this throughput limitation on the tested host.

### PCIe L0s isolation (2026-09-27)

The subsequent controlled comparison identifies an L0s-related performance
limit on this BCM70015/ICH8 link, not a general Gen1 x1 bandwidth ceiling.
The module, library, firmware and fixture were unchanged. Both ends of the
dedicated link initially enabled L0s and L1. Only the named ASPM bit was
temporarily changed, preserving L1/common-clock settings, link speed and
width, MPS and MRRS. The BIOS withholds OS ASPM control on this machine;
these direct configuration tests were explicitly authorized.

| Direct-library 900-picture run | Wall time | Mean picture submission-to-completion |
| --- | ---: | ---: |
| Original L0s/L1 enabled | 33.05 s | 34.741 ms |
| L1 disabled, L0s retained | No material improvement | 34.724 ms |
| Original settings restored | 33.06 s | 34.741 ms |
| L0s disabled, L1 retained | 21.13 s | 21.562 ms |
| Original settings restored again | 32.95 s | 34.735 ms |

Each trace pairs 902 submissions/completions: 900 pictures + two 160-byte
control outputs. All pictures, firmware EOS, empty ready queue and cleanup
pass. An initial L1 controller's unavailable log-check command failed after
decode; cleanup restored both ports and a corrected complete rerun passed.

Uninstrumented VA-API decode/download of the same 900-picture High MP4
improves from 27.26 fps / 33.59 s to 41.55 fps / 22.29 s with L0s disabled.
Both runs deliver 900/900 with zero drops or duplicates. Fresh 180-picture
NV12 outputs before/after have identical SHA-256
`3297f0792877072ea4f4cddf3ec4149ae52b1e42516465218a0b7d52156488f4`.
Both ports return to their original Link Control value afterward; the
kernel-error scan and endpoint AER counter comparison are clean. Module
references return to zero and global pin counters balance at
`126495681 / 126495681`.

The opt-in driver implementation (`force_l0s_off=1`), module source version
`11356398D0730685483E554`, reproduces 41.20 fps / 22.37 s for the same
900-picture VA-API run, with zero drops/duplicates and the identical fresh
180-picture hash above. With the option omitted, both Link Control words
remain unchanged and a direct-library 180-picture decode passes genuine EOS
and cleanup. With it enabled, only L0s changes at both link ends. Unloading
the module restores the original bits through the driver's BIOS-owned
fallback; the original module is then reloaded. This host does not exercise
the PCI-core-owned policy path, which deliberately stays disabled on unload.

Full `W=1`/`-Werror` and i386 checks pass. Production-helper/IRQ/PM fault suites
run old/current API masks and no-ASPM builds normally and under sanitizers:
3,439 checks per API-enabled run, 3,149 per no-ASPM run. Partial writes,
rollback, ownership, references, IRQ and fail-closed PM are mocked coverage,
not physical S3 or surprise removal.

At 1x, the numbered 1920x1080 H.264 High + AAC-LC clocked-sink test exposes
the original problem directly: with L0s enabled it stops after 81 pictures
at a 106.667 ms sampled A/V scheduling gap. The opt-in module passes a
timestamp-continuous 120-second version: 3,600/3,600 pictures in absolute
PTS/barcode order, 5,624 decoded audio buffers, EOS, 121.203 s wall time,
0.000 ms maximum measured A/V interval gap and 98,752 KiB peak RSS. The last
audio interval `[119.957333,119.978667]` overlaps the last video interval
`[119.966667,120]`; audio buffer count is not an exact sample-count claim.
The first sustained attempt incorrectly supplied the 12-second fixture to
a 120-second expectation and correctly failed at EOS after 360 pictures;
the module and link were restored, and the full-length fixture passed on
a fresh temporary module load.
