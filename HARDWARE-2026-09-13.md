# BCM70015 validation — 2026-09-13

This report distinguishes real card results from compile-only checks. It does
not close the complete [hardware matrix](https://github.com/ahnhy1324/crystalhd/issues/8).
The initial driver validation is commit `ba04191f02e3a79e81a5adba10105f761ab7b75e`,
merged into this fork only by [PR #10](https://github.com/ahnhy1324/crystalhd/pull/10)
represented by `cd5e7d0b92f1fd2cc2b37ebd7bf4121dda0567c8` after a privacy
rewrite that left driver code unchanged. All nine push and all nine pull-request CI jobs passed on
the equivalent original code. Follow-up codec/browser results below use the
commit containing this report, based on that merge; the kernel module is unchanged.

## Reference system

- PCI: Broadcom BCM70015, `14e4:1615`, `0000:02:00.0`.
- Kernel: Ubuntu `6.17.0-41-generic`, x86-64 with i386 userspace support.
- Firmware: `/lib/firmware/bcm70015fw.bin`, identical to the repository copy;
  SHA-256 `8bf3a68f5c64686358a52274e40911a88c7f8c67ecbf6cf1557a49b4d7bc67c9`.
- Library API reports driver `3.10.0`, DIL `3.22.0`. These version numbers do
  not distinguish source revisions; local library/frontend paths were forced.
- Final tested module source version: `8A4E42764F14473E9562951`.
  The complete repeated matrix also passed on `719593602CEFFABAD916D4F`;
  the final module additionally serializes firmware pause/resume callbacks.
- Full logs and generated samples are retained in a private local validation
  directory, outside this repository; they are not portable test prerequisites.

The PCI probe error cleanup now frees the driver's `pinfo` allocation, not the

input may still depend on it. The follow-up below explicitly preserves and
replays the original actual-IDR prefix instead.

## Follow-up: VA-API drain and seek

Final testing places the access-unit delimiter at the start of its own
timestamped packet. On sync demand after 100 ms grace, a finite submitted
batch can receive real EOS. New input stays queued until every submitted
timestamp and the hardware EOS marker complete. A full device reopen then
replays original compressed data from the retained actual IDR; duplicate
outputs cannot overwrite already-completed private pictures. Unknown/zero
timestamps are not guessed. Cache and replay limits fail honestly.

All three FFmpeg CLI runs produced exactly 62208000 bytes
(`640 × 360 × 1.5 × 180`) with no duplicate/drop counts. No replay reopen was
needed in these concurrent-input runs. Reported FFmpeg processing speeds were
2.94×, 2.90×, and 2.74× respectively; these are file-decode measurements, not
browser/display performance or guarantees for other clients.

| Profile | NV12 SHA-256 | Average software-comparison PSNR |
| --- | --- | --- |
| Baseline | `2fdc01576edbe9cb44a18c86f2751d6aa35784fd1a5b24b2e51c055674471b4f` | 44.576645 dB |
| Main | `68d9ad5cc5610b14741fa3bf3354f851d70fd42fd550e25730ba82db1f180a68` | 44.556008 dB |
| High | `b704ce0e449e7c1ab3077331c09b7aaa8b916aa2c7097dfaf54c43e520ba0ce0` | 44.555735 dB |

Luma PSNR exceeds 62.9 dB for all three. The coded VA surface is 640×368;
the container's visible 640×360 rectangle is what FFmpeg writes. Invalid
coded geometry or undersized destinations are rejected; unused larger client
regions are initialized. Failed CPU-write ownership operations are errors.

The default synchronous High seek probe drained the complete reference and
matched all 12 downloaded SHA-256 digests at each PTS target 46080, 23040,
69120, and 0 (stream time base 1/15360). It performed 47 full device reopens,
demonstrating the cost of a client without concurrent input. Final pins were
`16675615 / 16675615`, module references 0, and new kernel-error scans passed.
The three complete-file runs ended at `14697990 / 14697990` pins.

The optional `--lookahead 8` variant passed all three profiles independently,
each with a complete 180-frame reference and all four 12-frame pixel matches.
It retains a bounded set of future `AVFrame` objects using their own timestamps
and pixels, and leaves eight client pictures undownloaded before each seek,
releasing them before the flush. The retained-owner variant below adds checks
after the transition. This
is not a claim that all eight were still executing on hardware. Final pins
were `17796795 / 17796795`; the kernel-error scan passed. Software validation
also passes all three lookahead variants and the default High probe. CI runs
all three High software modes, including the retained-owner variant below.

Discarded channel-only-reset experiments did stall the firmware after 33
frames and logged firmware command/stop failures. The kernel disabled DMA,
cleanup eventually balanced `13143092 / 13143092` pins with zero references,
and a subsequent fresh GStreamer session passed 180/180 with the expected
baseline pixel hash without a reboot or module reload. The final replay path
does not use that failed decoder-only reset mechanism.

Both replay/geometry/ownership and 15 VPP lifecycle/fence regressions passed
ASan, UBSan, and leak checks. The full `make -j2 W=1 check` passed, including
staged loading, codec metadata/framing, and browser audit tests. These remain
separate from the hardware evidence above.

## Follow-up: browser identity audit

with the GPU sandbox enabled. A fresh temporary profile played a local

`c3b9c775ada7d35da71c66d042496f0e8eda19c447501929018e1a16c088f8ab`.

## Follow-up: VLC remains unvalidated

Installed VLC `3.0.21-11` was built with `--disable-crystalhd`. Both
`vlc-vaapi-v5.log` and `vlc-vaapi-gl-v5.log` in the report directory record
software fallback, not hardware passes. The dummy-output probe found no
matching hardware decoder. The GL probe loaded this CrystalHD VA-API backend,
but its VA-API converter failed because `vaAcquireBufferHandle` and
`vaReleaseBufferHandle` are unimplemented, then rejected hardware decoding.
This is an observed integration failure; the additional compatibility concerns
below have not all been established as runtime causes.

A native plugin would require the matching distro VLC SDK/plugin ABI: local
`vlc-plugin.pc` instead selects obsolete VLC `2.0.10` headers and libraries.
The upstream [plugin ABI definition](https://raw.githubusercontent.com/videolan/vlc/3.0.21/include/vlc_plugin.h)
and [native CrystalHD decoder](https://raw.githubusercontent.com/videolan/vlc/3.0.21/modules/codec/crystalhd.c)
also show why simply compiling the old module is not a playback validation:
its drain and seek/flush lifecycle needs adaptation and testing. For VA-API,
the [GL converter](https://raw.githubusercontent.com/videolan/vlc/3.0.21/modules/video_output/opengl/converter_vaapi.c)
requires buffer-handle support and a compatible exported plane layout;
external-read synchronization also needs review against the
[VA-API helper](https://raw.githubusercontent.com/videolan/vlc/3.0.21/modules/hw/vaapi/vlc_vaapi.c)
and [current backend](filters/vaapi/crystalhd_drv_video.cpp).
Neither a native plugin nor these export/synchronization changes were
implemented or validated in this run.

## Follow-up: live YouTube and legacy extension cleanup

The live YouTube demonstration exposed behavior not exercised by the local
barcode fixture. The externally installed H.264 extension 1.5.0 polls the
watch-page quality API every second to force a 480p range, and its seek overlay
can remain black if enough frame callbacks never arrive. Both behaviors also
run during software decoding. Chrome's Linux external registration loads this
package in fresh profiles independently of the unpacked-extension command-line
flag. These were not card-resolution limits or validated presentation fixes.

The codec-only 1.6.0 update removes the quality polling, poster hiding, and
entire seek overlay. Twenty-four real-source VM tests cover codec forwarding,
native errors/promises, optional API absence, and no DOM/player/timer effects.
The exact installed CRX and version registration were replaced with backups,
preserving the signing key and extension ID; unrelated managed policy and
