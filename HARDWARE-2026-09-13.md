This report distinguishes real card results from compile-only checks. It does
not close the complete [hardware matrix](https://github.com/ahnhy1324/crystalhd/issues/8).
The initial driver validation is commit `ba04191f02e3a79e81a5adba10105f761ab7b75e`,

The PCI probe error cleanup now frees the driver's `pinfo` allocation, not the
PCI-core-owned `pdev`, and clears the global pointer. Successful probe/reprobe
was tested via reload; allocation/PCI-enable failure injection was not run.

input may still depend on it. The follow-up below explicitly preserves and
replays the original actual-IDR prefix instead.

## Follow-up: VA-API drain and seek

Final testing places the access-unit delimiter at the start of its own
timestamped packet. On sync demand after 100 ms grace, a finite submitted
batch can receive real EOS. New input stays queued until every submitted
timestamp and the hardware EOS marker complete. A full device reopen then
replays original compressed data from the retained actual IDR; duplicate
outputs cannot overwrite already-completed private pictures. Unknown/zero
timestamps are not guessed. Cache and replay limits fail honestly.

All three FFmpeg CLI runs produced exactly 62208000 bytes
(`640 × 360 × 1.5 × 180`) with no duplicate/drop counts. No replay reopen was
needed in these concurrent-input runs. Reported FFmpeg processing speeds were
2.94×, 2.90×, and 2.74× respectively; these are file-decode measurements, not
browser/display performance or guarantees for other clients.

| Profile | NV12 SHA-256 | Average software-comparison PSNR |
| --- | --- | --- |
| Baseline | `2fdc01576edbe9cb44a18c86f2751d6aa35784fd1a5b24b2e51c055674471b4f` | 44.576645 dB |
| Main | `68d9ad5cc5610b14741fa3bf3354f851d70fd42fd550e25730ba82db1f180a68` | 44.556008 dB |
| High | `b704ce0e449e7c1ab3077331c09b7aaa8b916aa2c7097dfaf54c43e520ba0ce0` | 44.555735 dB |

Luma PSNR exceeds 62.9 dB for all three. The coded VA surface is 640×368;
the container's visible 640×360 rectangle is what FFmpeg writes. Invalid
coded geometry or undersized destinations are rejected; unused larger client
regions are initialized. Failed CPU-write ownership operations are errors.

The default synchronous High seek probe drained the complete reference and
matched all 12 downloaded SHA-256 digests at each PTS target 46080, 23040,
69120, and 0 (stream time base 1/15360). It performed 47 full device reopens,
demonstrating the cost of a client without concurrent input. Final pins were
`16675615 / 16675615`, module references 0, and new kernel-error scans passed.
The three complete-file runs ended at `14697990 / 14697990` pins.

The optional `--lookahead 8` variant passed all three profiles independently,
each with a complete 180-frame reference and all four 12-frame pixel matches.
It retains a bounded set of future `AVFrame` objects using their own timestamps
and pixels, and leaves eight client pictures undownloaded before each seek,
releasing them before the flush. The retained-owner variant below adds checks
after the transition. This
is not a claim that all eight were still executing on hardware. Final pins
were `17796795 / 17796795`; the kernel-error scan passed. Software validation
also passes all three lookahead variants and the default High probe. CI runs
all three High software modes, including the retained-owner variant below.

Discarded channel-only-reset experiments did stall the firmware after 33
frames and logged firmware command/stop failures. The kernel disabled DMA,
cleanup eventually balanced `13143092 / 13143092` pins with zero references,
and a subsequent fresh GStreamer session passed 180/180 with the expected
baseline pixel hash without a reboot or module reload. The final replay path
does not use that failed decoder-only reset mechanism.

Both replay/geometry/ownership and 15 VPP lifecycle/fence regressions passed
ASan, UBSan, and leak checks. The full `make -j2 W=1 check` passed, including
staged loading, codec metadata/framing, and browser audit tests. These remain
separate from the hardware evidence above.

### FHD bottleneck follow-up (2026-09-27)

The same uninterrupted 900-picture fixture (SHA-256
`fe186d05ceb384d38f6b674c98da84bd3285e00aee00651c001ea1d62b176d59`)
still falls below 1080p30. With module `8A4E42764F14473E9562951` and the
unchanged firmware, baseline `7373059` produced 900/900 at 27.30 fps;
fused SSE2 YUY2-to-NV12 conversion produced 900/900 at 27.29 fps. Neither
run dropped or duplicated frames. User CPU time fell from 17.41 to 15.94 s
(system time 2.94 to 3.06 s), but wall time stayed 33.58 s. This is a CPU
cost reduction, not a real-time or display-playback fix.

The conversion retains exact scalar rounding and odd-edge behavior. The
existing 316 comparisons plus 1,170 exact-allocation/alignment cases pass;
both SSE2 and scalar-fallback replay suites pass ASan/UBSan/leak checks.
A fresh before/after decode of the 180-picture High fixture above yields
identical 559,872,000-byte NV12 output, SHA-256
`3297f0792877072ea4f4cddf3ec4149ae52b1e42516465218a0b7d52156488f4`.
This is current-baseline equivalence, not a new independent software comparison.

Direct-library no-copy decoding also returns all 900 pictures, genuine
firmware EOS and clean teardown in 33.05 s, using only 6% CPU. Kernel probes
pair all 902 RX submissions/completions (including control outputs): average
submission-to-completion 34.703 ms, with 14–15 free capture buffers at posting.
Picture-ready notification to posting is 8–32 microseconds. The long interval
includes firmware and device transfer; it does not prove PCIe saturation.

A bounded temporary kernel experiment reduced the RX scatterlist from
per-page entries to an average of 608 entries, but still measured 27.20 fps
and 34.802 ms submission-to-completion. It was excluded and the original
module restored; no installation or PCIe settings changed. Observing the
driver's existing startup register read returned DMA debug value `0x10`,
with single-read/write-queue bits clear; this is not a runtime occupancy test.

The library now forwards the existing TX-only status-request bit to avoid
unrequested RX metadata peeks. Actual public/internal/ioctl-path tests fail
10 of 104 checks before the fix and pass all 104 afterward on native/i386
and under sanitizers. Legacy VC-1 FIFO-selection behavior is unchanged.
Final retained-code validation passes `make -j2 W=1 check` and the i386
userspace suite. After restoring the original module, an uninstrumented
900/900 run measures 27.28 fps (33.59 s; user/system 15.99/3.02 s), with no
drops/duplicates, new kernel errors or module references; global pin counters
balance at `115309611 / 115309611`.
Issue #8 remains open for real-time FHD and its other unchecked coverage.

### PCIe L0s isolation (2026-09-27)

The subsequent controlled comparison identifies an L0s-related performance
limit on this BCM70015/ICH8 link, not a general Gen1 x1 bandwidth ceiling.
The module, library, firmware and fixture were unchanged. Both ends of the
dedicated link initially enabled L0s and L1. Only the named ASPM bit was
temporarily changed, preserving L1/common-clock settings, link speed and
width, MPS and MRRS. The BIOS withholds OS ASPM control on this machine;
these direct configuration tests were explicitly authorized.

| Direct-library 900-picture run | Wall time | Mean picture submission-to-completion |
| --- | ---: | ---: |
| Original L0s/L1 enabled | 33.05 s | 34.741 ms |
| L1 disabled, L0s retained | No material improvement | 34.724 ms |
| Original settings restored | 33.06 s | 34.741 ms |
| L0s disabled, L1 retained | 21.13 s | 21.562 ms |
| Original settings restored again | 32.95 s | 34.735 ms |

Each reported trace pairs all 902 submissions/completions, separating 900
picture outputs from two 160-byte control outputs. Each probe returns all
900 timestamped pictures, the firmware EOS marker, an empty ready queue and
clean teardown. The first L1 controller hit an unavailable log-check command
after successful decoding; its cleanup restored both ports, and a corrected
controller repeated the complete test successfully.

Uninstrumented VA-API decode/download of the same 900-picture High MP4
improves from 27.26 fps / 33.59 s to 41.55 fps / 22.29 s with L0s disabled.
Both runs deliver 900/900 with zero drops or duplicates. Fresh 180-picture
NV12 outputs before/after have identical SHA-256
`3297f0792877072ea4f4cddf3ec4149ae52b1e42516465218a0b7d52156488f4`.
Both ports return to their original Link Control value afterward; the
kernel-error scan and endpoint AER counter comparison are clean. Module
