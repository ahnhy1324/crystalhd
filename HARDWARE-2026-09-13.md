# BCM70015 validation — 2026-09-13

This report distinguishes real card results from compile-only checks. It does
not close the complete [hardware matrix](https://github.com/ahnhy1324/crystalhd/issues/8).
The corresponding source is the commit containing this report, based on
`08df603f272c18cf5733c81f0e12be4ae80d5f85`.

## Reference system

- PCI: Broadcom BCM70015, `14e4:1615`, `0000:02:00.0`.
- Kernel: Ubuntu `6.17.0-41-generic`, x86-64 with i386 userspace support.
- Firmware: `/lib/firmware/bcm70015fw.bin`, identical to the repository copy;
  SHA-256 `8bf3a68f5c64686358a52274e40911a88c7f8c67ecbf6cf1557a49b4d7bc67c9`.
- Library API reports driver `3.10.0`, DIL `3.22.0`. These version numbers do
  not distinguish source revisions; local library/frontend paths were forced.
- Final tested module source version: `8A4E42764F14473E9562951`.
  The complete repeated matrix also passed on `719593602CEFFABAD916D4F`;
  the final module additionally serializes firmware pause/resume callbacks.
- Local full logs and generated samples: `PRIVATE_LOCAL_VALIDATION_DIRECTORY`.
  That directory is not part of the repository or a portable test prerequisite.

## Results

| Test | Evidence and boundary |
| --- | --- |
| `make -j2 W=1 check` | Passed locally: module/userspace build, frozen native/compat ABI, ASan/UBSan descriptor tests, discovery, H.264 generation, imported surfaces, browser probe regression tests, staged library/plugin loading. Does not decode video on the card. |
| Native/compat ioctl probe | 43 checks passed per architecture, including malformed requests, permission checks, legacy color controls, guarded user copies, and partial/failed capture pinning. No firmware or compressed input in this probe. |
| 32-/64-bit library | Complete libraries and examples build; both API probes successfully open firmware, query version/capabilities, change YUY2/UYVY output mode, and close. |
| GStreamer H.264 | Baseline/Main/High each decode all 180 frames and drain; flushing seek-to-zero replay produces all 180 frames with identical visible-pixel SHA-256. This is EOS replay, not arbitrary in-flight seeking. |
| GStreamer MPEG-2 Main | One progressive sample drains to exactly 180 YUY2 frames. |
| Competing playback clients | A second GStreamer client is rejected with driver status 13 and reports 0/180 frames as failure. The first client still drains all 180 frames; another standalone decode then passes 180/180 with the baseline pixel hash. Pins settle to `4234355 / 4234355`. |
| Module unload/reload | Passed repeatedly while idle. After loading the final module, both ioctl architectures pass again, all three H.264 profiles drain and replay identically, and busy-client rejection followed by another complete decode passes. Final settled pin counters: `8846573 / 8846573`; module reference count: 0. |
| VA-API H.264 | **Not passing:** strict complete-file validation exposes missing final output and an EOF wait. Earlier frame-count-only or blank-frame results must not be treated as proof of correct complete decoding. |
| VA-API seek probe | Software self-check passes 180 reference frames plus four seeks with 12 exact PTS/pixel matches each. Hardware validation is blocked by incomplete reference drain. |
| DMA pin accounting | Global `nr_foll_pin_acquired` and `nr_foll_pin_released` settle to equal values after GStreamer exits and after timed-out VA-API processes are terminated. For example: `3232593 / 3232593` after the decode-order experiment. These global counters are supporting evidence, not per-device DMA-map instrumentation. |

Expected malformed-ioctl rejections appear in the kernel log during the ioctl
probe. Playback runs are checked separately for new kernel warnings/errors;
ordinary playback and forced VA-API process cleanup produced no new kernel
oops, BUG, hung-task report, or observed outstanding pins. This does not cover
injected PCI stop failures, concurrent suspend, or physical removal during DMA.
The final playback log starts at `10:47:26.825271 +09:00`, after the ioctl
probe's deliberate failures. Test scripts use microsecond-resolution start
times to avoid including earlier expected failures from the same second.

The PCI probe error cleanup now frees the driver's `pinfo` allocation, not the
PCI-core-owned `pdev`, and clears the global pointer. Successful probe/reprobe
was tested via reload; allocation/PCI-enable failure injection was not run.
Kernel Kbuild uses `-Werror` and CI adds `W=1`; GStreamer and VA-API also use
`-Werror`. The legacy library and examples do not yet enable it globally.

The VA-API backend now bounds an otherwise infinite synchronization wait at
10 seconds and reports `VA_STATUS_ERROR_DECODING_ERROR`. Hardware testing
confirmed FFmpeg exits with an error instead of hanging. A firmware experiment
requested decode order both at startup and with `SET_DISPLAY_ORDER`; the
subsequent `GET_DISPLAY_ORDER` still reported display order. The ineffective
opt-in API/commands were removed. Firmware flush modes that inject H.264
end-of-sequence cannot be used on an ordinary synchronization call: later
non-IDR input may still arrive and depend on the existing reference pictures.

## Reproduction

Build the repository, load that exact module while the device is idle, and
compare `/sys/module/crystalhd/srcversion` with `modinfo -F srcversion
driver/linux/crystalhd.ko`. No preexisting player may use the card during the
probes. The following commands use the in-tree library/frontend:

```sh
sh tests/ioctl-smoke.sh
sh tests/userspace32.sh --hardware
sh tests/generate-h264-samples.sh /tmp/crystalhd-profile-samples
for profile in baseline main high; do
  CRYSTALHD_TEST_SEEK=1 sh tests/gstreamer-hardware.sh \
    "/tmp/crystalhd-profile-samples/$profile.mp4" 2
done
CRYSTALHD_TEST_TIMEOUT=20 sh tests/vaapi-hardware-stress.sh \
  /tmp/crystalhd-profile-samples/baseline.mp4 1
```

All profile samples are six seconds, 640×360, progressive YUV420p, 30 fps,
180 frames, MP4 containing H.264 with a one-second closed GOP. GStreamer's
parser converts to Annex-B access units. Checksums depend on the encoder
version; the exact samples used here have these SHA-256 values:

| Profile | Input file SHA-256 | Decoded YUY2 visible pixels SHA-256 |
| --- | --- | --- |
| Constrained Baseline | `3fdd8b30ef7a51fe302e21e4355b09dbf4dc73fd3b4312ff59eba7bdf6ebf7f7` | `36eacf204308613a78b61bb1fa52fd8ffa2a06adfab07bb8172e9606f2eb9313` |
| Main | `7d6a455a7ee86545a65d7357b9b1d9d7bd957012fca68593485c86cc1abb7999` | `d82a6ba190a6fdbaa1c857b71ee5699de74899036e2ff28cbdc75133ec526583` |
| High | `1b6ad927b660238dfabc4c25531439d4ea16d0742f249427784bc575e6270eec` | `561709f74ee7fb12498cb714035cb837a9cfdf1d395c6c1bcc98a7cf514ddda2` |

MPEG-2 was generated and tested as follows (use a fresh output directory):

```sh
ffmpeg -nostdin -hide_banner -loglevel error -n \
  -f lavfi -i testsrc2=size=640x360:rate=30 -frames:v 180 \
  -an -c:v mpeg2video -q:v 4 -g 30 -bf 2 -f mpeg2video mpeg2.m2v
GST_PLUGIN_PATH="$PWD/filters/gst/gst-plugin-1.0" \
LD_LIBRARY_PATH="$PWD/linux_lib/libcrystalhd" \
timeout --foreground --kill-after=10 30 \
  gst-launch-1.0 -q filesrc location=mpeg2.m2v ! mpegvideoparse ! \
  crystalhddec ! filesink location=mpeg2-output.yuy2
stat -c %s mpeg2-output.yuy2
```

The output is `82944000` bytes (`640 × 360 × 2 × 180`), with successful EOS.
Input SHA-256: `32d8ca6ddf8ad529ae3875ee9b7e904630c633bfef6d74ba40d7b1040d20820b`.
Output SHA-256: `d09417c749fd6460667e4e1c3b6d4c1d66af81e85426f825cfbaf1a39f1ae8d1`.
